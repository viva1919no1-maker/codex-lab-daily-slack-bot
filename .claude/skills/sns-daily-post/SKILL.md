# SNS Daily Post Pipeline（vivaのSNS自動運用）

出典: https://x.com/beku_ai/status/2069008315951260128 で解説されていた「Claude CodeでX/Threadsを自動運用する仕組み」をvivaの事業向けに落とし込んだもの。

考え方: 毎日1本ひねり出すのではなく、毎日いい投稿が勝手に出てくる仕組みを作る。そのために必要な3つの材料を `knowledge/` に資産として溜め、4工程のパイプラインで回す。

## 3つの材料

1. **口調** (`knowledge/voice-profile.md`) — vivaらしい文体。AIにそのまま書かせると無味無臭になるので、過去投稿から文体プロファイルを作って読ませる。
2. **伸びる型** (`knowledge/patterns/*.md`) — 伸びている投稿の構造パターン。パターンごとに1ファイル。
3. **伸びるネタ** (`knowledge/topics-backlog.md`) — 直近で伸びているテーマ・競合投稿・最新ニュース。

どれか1つでも空だと出力は平凡になる。生成前に3つとも埋まっているか確認すること。

## 初回セットアップ: 口調プロファイルを作る

`knowledge/voice-profile.md` が空のままなら、vivaの過去投稿（X/Threads含め最低20〜30本目安）を集めてもらい、以下のプロンプトで分析し、結果を `knowledge/voice-profile.md` に書き出す。

口調分析プロンプト:
```
あなたはSNS文章の文体アナリストです。
これから渡す私の過去ポスト群を読み込み、別のAIが私の文体を高い精度で再現できるようにするための「文体プロファイル」を作成してください。
目的は、単に雰囲気を真似ることではありません。
私が普段どのような言葉選び、テンポ、構成、感情表現で読者に伝えているのかを、再現可能なルールとして言語化することです。
以下の観点で分析してください。
1. 基本トーン
- 親しみやすい／断定的／煽り気味／冷静／熱量高めなど
- 読者との距離感
- 上から目線に見えないための言い回し
2. 文体の特徴
- 一人称
- 常体と敬体の比率
- 語尾のクセ
- 一文の平均的な長さ
- 短文と長文の使い分け
- 改行のタイミング
- 句読点の使い方
- 記号、絵文字、カタカナ語の使用傾向
3. 構成のクセ
- 冒頭でよく使う入り方
- 問題提起の仕方
- 主張から入るか、共感から入るか、結論から入るか
- 具体例を出すタイミング
- 読者に行動を促すときの自然な流れ
4. よく使う表現
- 頻出する言い回し
- 口癖
- 決め台詞
- 逆によく使わない言葉
```

以後の生成では必ず `knowledge/voice-profile.md` を読み込み、「このプロファイルに従って書く」と明示すること。投稿を重ねて口調がズレてきたら同じプロンプトで再分析し、上書きする。

## 伸びる型を追加する

新しいパターンを見つけたら `knowledge/patterns/` に1ファイル追加する。テンプレートは `knowledge/patterns/_template.md` を参照。最低限書くこと:
- パターン名
- フック（冒頭1〜2文）の作り方
- 本文の構成順序
- 想定文字数
- CTA（行動喚起）の入れ方
- 実例（URLまたは本文の引用）

## 工程1: 伸びるネタのリサーチ

実行内容:
- vivaのジャンルで直近伸びている投稿をX/Threads/YouTube/Instagramを横断して調べる（WebSearch、または利用可能なMCPツールがあれば使う）
- エンゲージメントが高かった自分の過去投稿のテーマを振り返る
- 最新ツール・ニュースで話題になっているものを拾う

集めた候補は `knowledge/topics-backlog.md` に追記する（日付・テーマ・出典・伸びそうな理由・使用済みフラグ）。同じネタを使い続けないよう、生成時は未使用のものから選ぶ。

## 工程2: 投稿生成

1. `knowledge/voice-profile.md`、該当する `knowledge/patterns/*.md`、`knowledge/topics-backlog.md` の未使用ネタを読み込む
2. 「このプロファイルの口調で、この型の構成に沿って、このネタについて書く」と明示して本文を生成する
3. プラットフォームごとに最適化する（X: 短文寄りでテンポ重視、Threads: やや長文でも質が良ければ読まれる）

## 工程3: ファクトチェックと品質チェック — 必ず別人格でレビューする

書いた本人（同じコンテキスト）がそのままチェックすると見落としが起きる。書く工程とは別に Agent tool で新しいエージェント（subagent_type: general-purpose）を立て、ドラフトの執筆意図を渡さずレビューだけさせる。

ファクトチェック観点:
- 数値・固有名詞・引用の正確性（ハルシネーション確認）
- 言及したツール・サービス・リンク先の実在性

品質チェック観点:
- フックが弱くないか（冒頭1文で離脱されないか）
- 語尾が単調でないか
- 中身が薄くないか（具体性があるか）

基準に届かなければ工程2に戻して書き直す。レビュー結果はSlackの承認メッセージに要約として添える。

## 工程4: Slackへの承認依頼

このリポジトリの主目的（daily-slack-bot）に合わせ、生成・チェック済みの下書きは即時SNSに出さず、まずSlackに承認依頼として送る。

`mcp__Slack__slack_send_message`（または朝の定刻配信なら `slack_schedule_message`）で承認チャンネルに以下を含めて送る:
- プラットフォーム（X / Threads）
- 投稿本文（下書き）
- 使ったネタの出典
- 使った型
- ファクトチェック/品質チェックの結果サマリ

vivaが承認（リアクション等）したら本番投稿に進める。X/Threadsへの実際のAPI投稿はこのスキルの範囲外 — 各プラットフォームの公式API連携が未設定な間は、承認後の本文をviva自身が手動投稿する暫定運用とする。

## プラットフォームの選び方

- フォロワーが少ない新規・育成中アカウントは **Threads** から始める。フォロワー数に関係なく質で伸びるため初動が出やすい。
- 仕組みが固まり運用に慣れたら **X** にも横展開する。Xは初期アカウントだとアルゴリズム的に伸びにくいので後回しでよい。
